# Проєкт REST API: Інформаційна система «Події та клуби»

## 1. Ресурси та зв’язки

Інформаційна система призначена для обліку клубів коледжу, організації подій цими клубами та реєстрації учасників на події.

| Ресурс | Атрибути (тип) | Зв’язки |
|---|---|---|
| `clubs` (клуби) | `id` (integer, readOnly), `name` (string), `description` (string), `leaderId` (integer), `createdAt` (date-time, readOnly), `isActive` (boolean) | Клуб має багато подій; керівник відповідає за створення подій свого клубу |
| `events` (події) | `id` (integer, readOnly), `clubId` (integer), `title` (string), `description` (string), `location` (string), `startsAt` (date-time), `capacity` (integer), `status` (enum: planned, cancelled, completed), `createdBy` (integer, readOnly), `createdAt` (date-time, readOnly) | Подія належить одному клубу та має багато реєстрацій |
| `registrations` (реєстрації) | `id` (integer, readOnly), `eventId` (integer), `participantId` (integer), `participantName` (string), `participantEmail` (email), `registeredAt` (date-time, readOnly), `status` (enum: active, cancelled) | Реєстрація належить одній події; подія має багато реєстрацій |

Атрибути `id`, `createdAt`, `createdBy`, `registeredAt` призначаються сервером і не передаються клієнтом під час створення. `status` події змінюється спеціальною дією скасування, а не довільним оновленням через PATCH. Для реєстрації діє обмеження унікальності пари `eventId + participantId`.

## 2. Таблиця маршрутів

Базова адреса: `http://localhost:3000/api/v1`

| № | Метод | Шлях | Призначення | Успіх | Помилки | Хто має доступ |
|---:|---|---|---|---|---|---|

| 5 | PATCH | `/clubs/{clubId}` | Часткове оновлення клубу | 200 | 400, 401, 403, 404, 422 | адміністратор або керівник клубу |
| 6 | DELETE | `/clubs/{clubId}` | Видалення клубу без подій | 204 | 401, 403, 404, 409 | адміністратор |
| 7 | GET | `/events` | Список подій із фільтрами та сторінками | 200 | 400, 401 | автентифіковані |

| 13 | POST | `/events/{eventId}/registrations` | Реєстрація учасника на подію | 201 + Location | 400, 401, 404, 409, 422 | автентифіковані |
| 14 | GET | `/registrations/{registrationId}` | Отримання реєстрації | 200 | 401, 404 | власник або керівник клубу |

| 16 | POST | `/events/{eventId}/cancellation` | Скасування події (зміна стану) | 200 | 401, 403, 404, 409 | лише керівник клубу |

## 3. Фільтрація, сортування, пагінація

| Колекція | Параметри фільтрації | Сортування | Пагінація |
|---|---|---|---|
| `/clubs` | `isActive`, `leaderId`, `name` (частковий пошук) | `name`, `-name`, `createdAt`, `-createdAt` | `page` від 1, `pageSize` від 1 до 50; типово 10 |
| `/events` | `clubId`, `status`, `startsAfter`, `startsBefore`, `location` | `startsAt`, `-startsAt`, `createdAt`, `-createdAt`, `title` | `page` від 1, `pageSize` від 1 до 50; типово 10 |
| `/events/{eventId}/registrations` | `status`, `participantId` | `registeredAt`, `-registeredAt`, `participantName` | `page` від 1, `pageSize` від 1 до 50; типово 10 |

Усі колекції повертаються у форматі `{ "items": [], "page": 1, "pageSize": 10, "total": 0 }`. Сортування за спаданням позначається префіксом `-`.

## 4. Проєктні рішення

| Питання | Рішення та обґрунтування |
|---|---|
| Як змінюється стан ресурсу (дія)? | Скасування події виконується `POST /events/{eventId}/cancellation`. Дія доступна лише керівнику клубу. Подію зі статусом `completed` або вже `cancelled` повторно скасувати не можна; сервер повертає 409. Реєстрації після скасування події стають недійсними для участі. |
| Які методи ідемпотентні у вашому API? | GET, PATCH за однакового тіла, DELETE та PUT (якби був передбачений) є ідемпотентними за семантикою HTTP. POST створення не є ідемпотентним; для повторних запитів створення реєстрації використовується унікальність `eventId + participantId` та відповідь 409, щоб не створювати дублікати. |
| Як версіонується API? | Версія задається у шляху: `/api/v1`. Несумісні зміни (видалення/перейменування поля, зміна типу або обов’язковості) реалізуються в `/api/v2`. Перехідний період оголошується заголовками `Deprecation: true` і `Sunset` із датою припинення підтримки v1. |
| Формат помилок | Усі помилки повертаються як `application/problem+json` за RFC 9457 з полями `type`, `title`, `status`, `detail`, `instance`. Помилки перевірки даних додатково містять `errors` з назвою поля та повідомленням. |
| Як клієнт дізнається адресу створеного ресурсу? | Відповідь на успішний POST має код 201 Created і заголовок `Location` з URI створеного ресурсу. Тіло відповіді містить створений об’єкт. |
| Які операції підтримують умовні запити (ETag)? | GET одного клубу, події або реєстрації повертає ETag; клієнт може передати If-None-Match і отримати 304 без тіла. PATCH підтримує If-Match; за застарілого ETag сервер повертає 412 Precondition Failed. |

## 5. Самоперевірка

- [x] Шляхи – іменники в множині, kebab-case, без дієслів.
- [x] Методи використано за семантикою HTTP.
- [x] Створення повертає 201 + Location, видалення – 204.
- [x] Для операцій описано клієнтські помилки; захищені операції мають 401.
- [x] Колекції повертають сторінку `{ items, page, pageSize, total }`.
- [x] Для створення подій передбачено обмеження за роллю керівника клубу.
- [x] Дія скасування події позначена як окрема операція.
- [ ] `npm run lint` – перевірити після встановлення залежностей.
