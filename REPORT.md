## 1. Мета роботи

Набути практичних навичок проєктування REST API за підходом design-first: визначати ресурси та їх зв’язки, будувати маршрути відповідно до семантики HTTP, обирати коди станів, проєктувати фільтрацію, сортування й пагінацію, описувати формат помилок і версіонування, створювати специфікацію OpenAPI 3.1 та перевіряти її.

## 3. Виконання роботи

### Завдання 1–4. Проєктування API

Розроблено REST API інформаційної системи «Події та клуби». Визначено три основні ресурси: `clubs`, `events`, `registrations`. Подія належить клубу, а реєстрація належить події. Сервер самостійно призначає ідентифікатори та дати створення.

У `DESIGN.md` наведено 16 маршрутів, серед яких операції отримання колекцій, створення, читання, часткового оновлення, видалення, вкладена колекція реєстрацій і дія скасування події. Для колекцій передбачено фільтрацію, сортування та пагінацію. Створення події обмежено роллю керівника відповідного клубу.

### Завдання 5. Взаємне рецензування

Фактичний обмін файлами з одногрупником має бути виконаний окремо. Для самоперевірки використано такі контрольні зауваження та виправлення:

| № | Можливе зауваження під час рецензування | Виправлення в проєкті |
|---:|---|---|
| 1 | У шляху не можна використовувати дієслово | Використано іменники `events`, `registrations`, `cancellation`; дію визначає HTTP-метод POST |
| 2 | Створення ресурсу має повертати 201 і Location | Для POST створення описано відповідь 201 Created із заголовком Location |
| 3 | Видалення має повертати 204 | Для DELETE визначено 204 No Content |
| 4 | Для захищених операцій необхідно описати 401 | Додано відповіді 401 до захищених операцій |
| 5 | Необхідно врахувати роль керівника клубу | Для створення та скасування подій описано обмеження ролі й відповідь 403 |

### Завдання 6–7. Специфікація OpenAPI

Створено файл `openapi.yaml` версії OpenAPI 3.1.0. Описано схеми клубу, події та реєстрації, окремі схеми створення й оновлення, схеми сторінок колекцій, параметри пагінації, Bearer-автентифікацію та повторно використовувані відповіді помилок.

Для створення ресурсів визначено 201 Created і Location. Для видалення — 204 No Content. Для помилок використано `application/problem+json` за RFC 9457. Дію скасування події позначено `x-kss-action: true`.

Додатково описано умовні запити: ETag, If-None-Match, If-Match, відповіді 304 і 412.

### Завдання 8. Автоматична перевірка

Команди для перевірки:

```bash
npm install
npm run lint
```

У середовищі виконання цієї підготовки доступна версія Node.js 22, тоді як стартовий проєкт вимагає Node.js 24 або новішу. Тому остаточний запуск Spectral необхідно виконати локально після встановлення Node.js 24 LTS.

Перед здачею потрібно вставити сюди скріншот фактичного результату `npm run lint` та за потреби доповнити таблицю п’ятьма повідомленнями, які реально вивів лінтер. Не слід зазначати, що перевірку пройдено, доки команда не завершилася без помилок.

| Правило / тип помилки | Що перевірити | Як виправляється |
|---|---|---|
| `kss-server-versioned` | Версія в адресі сервера | Завершити адресу на `/api/v1` |
| `kss-path-kebab-case` | Формат сегментів шляху | Використовувати малі літери та дефіси |
| `kss-post-creates-resource` | Код створення та Location | Додати 201 і заголовок Location |
| `kss-delete-no-content` | Код успішного DELETE | Додати 204 No Content |
| `kss-paged-collections` | Параметри й структура колекції | Додати page, pageSize та items/page/pageSize/total |

### Завдання 9. Документація та імітаційний сервер

Після успішного встановлення залежностей виконати:

```bash
npm run docs
npm run mock
```

Документація створюється у `docs/index.html`. Імітаційний сервер запускається на `http://localhost:4010`.

Приклади перевірки після запуску Prism (маршрути mock-сервера використовуються без `/api/v1`):

```bash
# Отримання без токена — очікується 401
curl -i http://localhost:4010/events

# Запит із токеном — перевірка захищеного маршруту
curl -i -H "Authorization: Bearer test" http://localhost:4010/events

# Створення події — приклад коректного JSON
curl -i -X POST http://localhost:4010/events \
  -H "Authorization: Bearer test" \
  -H "Content-Type: application/json" \
  -d '{"clubId":1,"title":"День програмування","description":"Зустріч учасників клубу","location":"Актова зала","startsAt":"2027-03-20T12:00:00Z","capacity":50}'
```

Для звіту необхідно зробити власні скріншоти: відкритої документації, відповіді 201 із Location, відповіді 422 для некоректного тіла та відповіді 401 без токена. Результати цих запусків не підмінюються текстовими прикладами.

## 4. Відповіді на контрольні запитання

**1. Що таке ресурс і представлення ресурсу? Чому шляхи містять іменники, а не дієслова?**

Ресурс — це об’єкт предметної області, який має URI, наприклад клуб, подія або реєстрація. Представлення ресурсу — це дані про нього у визначеному форматі, наприклад JSON. Шляхи містять іменники, тому що ресурс визначає, з чим працює клієнт, а дію над ним визначає HTTP-метод: GET, POST, PATCH або DELETE.

**2. Як моделювати дію, що не вкладається в CRUD? Наведіть приклад зі свого варіанта.**

Таку дію можна описати окремим підресурсом і методом POST. У цьому проєкті скасування події виконується запитом `POST /events/{eventId}/cancellation`. Дія змінює статус події на `cancelled`. Її може виконати лише керівник відповідного клубу. Якщо подію вже скасовано або завершено, повертається 409 Conflict.

**3. Які методи HTTP безпечні та ідемпотентні? Навіщо це знати, проєктуючи API?**

Безпечним є GET, оскільки він не повинен змінювати стан сервера. Ідемпотентними є GET, HEAD, OPTIONS, PUT і DELETE. Повторення такого самого запиту не повинно змінювати результат після першого виконання. Це важливо для повторних запитів після мережевих збоїв і запобігання небажаним дублюванням.

**4. Чим відрізняються коди 400, 409 і 422? 401 і 403? Коли повертати 204?**

400 означає, що запит некоректний або не може бути розібраний. 409 означає конфлікт із поточним станом ресурсу. 422 означає, що формат запиту правильний, але дані не проходять перевірку. 401 означає відсутню або недійсну автентифікацію, а 403 — що користувача впізнано, але йому не вистачає прав. 204 повертається, коли операція успішна і тіло відповіді не потрібне, наприклад після DELETE.

**5. Порівняйте пагінацію зі зміщенням (page/pageSize) і курсорну. Коли доцільна кожна?**

Пагінація `page/pageSize` ділить результат на сторінки за номером і розміром. Вона проста для користувача й зручна для невеликих або відносно стабільних наборів даних. Курсорна пагінація використовує позиційний маркер останнього отриманого запису. Вона краще підходить для великих і часто змінюваних колекцій, оскільки зменшує проблеми зі зміщенням записів між сторінками.

**6. Які способи версіонування API ви знаєте? Які зміни вимагають нової версії?**

Версію можна передавати в URI, заголовку запиту або через тип медіа. У цьому проєкті використовується версія в URI — `/api/v1`. Нової версії потребують несумісні зміни: видалення або перейменування поля, зміна його типу, зміна обов’язковості чи зміна структури відповіді, яка порушує роботу старих клієнтів.

**7. З яких розділів складається специфікація OpenAPI? Навіщо components і $ref?**

Основні розділи OpenAPI: `openapi`, `info`, `servers`, `tags`, `paths` і `components`. У `paths` описуються маршрути й операції, а в `components` зберігаються спільні схеми, параметри, відповіді та механізми безпеки. `$ref` дає змогу посилатися на вже описані компоненти, уникати дублювання та підтримувати узгодженість специфікації.

**8. Що дає підхід «спершу проєкт» (design-first) порівняно з генерацією специфікації з коду?**

Підхід design-first передбачає, що спочатку визначають ресурси, маршрути, формати даних і відповіді, а вже потім реалізують програмний код. Це дає змогу узгодити API до початку розробки, раніше виявити помилки проєктування та паралельно працювати над клієнтською і серверною частинами. Генерація з коду починається з реалізації, тому помилки структури API можуть виявитися пізніше.

## 5. Відомості про використання ШІ

Під час підготовки проєкту використовувався ChatGPT як допоміжний інструмент для структурування проєктної документації, підготовки прикладу специфікації OpenAPI 3.1, перевірки узгодженості назв ресурсів і формування відповідей на контрольні запитання. Остаточну перевірку специфікації, запуск команд і тестування імітаційного сервера виконує здобувач самостійно.

Під час практичної роботи спроєктовано REST API для інформаційної системи «Події та клуби». Передбачено рольові обмеження, фільтрацію, сортування, пагінацію, автентифікацію та формат помилок Problem Details. Створено специфікацію OpenAPI 3.1 з повторно використовуваними компонентами.
